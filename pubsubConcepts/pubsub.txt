                    REDIS PUB/SUB (PUBLISH / SUBSCRIBE) CONCEPTS
================================================================================

1. WHAT IS REDIS PUB/SUB?
--------------------------------------------------------------------------------
Pub/Sub stands for "Publish and Subscribe". It is a messaging pattern where:
- Publishers do not send messages directly to specific receivers (subscribers).
- Instead, publishers broadcast messages to a topic or "Channel" without knowing
  who (if anyone) is listening.
- Subscribers express interest in one or more channels and only receive messages
  that are sent to those channels.

Analogy:
Think of Pub/Sub like a traditional FM Radio Station:
- Radio Station (Publisher): Broadcasts audio waves over frequency 98.3 FM (Channel).
  The station does not know or care how many cars are tuned in.
- Listeners (Subscribers): Turn their car radio dial to 98.3 FM. As long as their
  radio is turned on, they hear the music live.
- Missed Music: If your radio was turned off when a song played, you missed it.
  The radio station does not replay it for you or save it on your radio.

3. CODE ANALYSIS: WHAT WE IMPLEMENTED
--------------------------------------------------------------------------------

We implemented Pub/Sub across two layers:

A. Educational Demo Script (examples/redis-pub-sub.ts):
   - Created two separate Redis clients: "publisher" and "subscriber".
   - Demonstrated that the subscriber must subscribe BEFORE the publisher sends events.
   - Captured the return value of `publish()`, which is an integer indicating the
     number of active subscribers that received the message.
   - Showed clean teardown: `unsubscribe()` and `quit()`.

B. Full Application Feature (src/):
   1. Route (src/routes/notification.routes.ts):
      - Exposes `POST /notification` using Express Router.
      - Registered under `/api/notification` in `src/routes/index.ts`.
   
   2. Controller (src/controllers/notification.contoller.ts):
      - Extracts dynamic payload `{ title, message }` from `req.body`.
      - Adds metadata: `id: Date.now().toString()` and `createdAt: new Date().toISOString()`.
      - Calls `publishNotification(notification)`.
      - Returns HTTP 200 `{ success: true, message: "notification published successfully" }`.

   3. Subscriber & Publisher Service (src/subscribers/notification.subscriber.ts):
      - Channel Name: `"notifications"`
      - Publisher: Uses the app's global `redisClient` to call:
        `await redisClient.publish(notification_channel, JSON.stringify(notification))`
      - Subscriber: Creates a standalone `subsciberClient = createClient({ url })`,
        connects, and listens via `subsciberClient.subscribe()`.
   
   4. NPM Script (package.json):
      - `"subscriber": "tsx src/subscribers/notification.subscriber.ts"`
      - Runs in a separate terminal tab as a background worker process.


4. DEEP DIVE: WHY TWO DIFFERENT REDIS CLIENT CONNECTIONS?
--------------------------------------------------------------------------------
One of the most common questions in Redis Pub/Sub:
"Why does the subscriber need its own client, but the publisher does not?"

1. Publisher uses `redisClient`:
   - Publishing (`redisClient.publish()`) is a standard, non-blocking Redis command.
   - It executes immediately and returns the number of recipients.
   - It can share the exact same Redis connection that handles `get`, `set`, and
     `incr` for products and rate limiting.

2. Subscriber requires a DEDICATED `subscriberClient`:
   - When a Redis client issues the `SUBSCRIBE` command, the Redis RESP protocol puts
     that specific socket connection into a restricted "Subscriber Mode".
   - In Subscriber Mode, the connection is blocked from executing ordinary commands
     like `GET`, `SET`, `HSET`, or `INCR`. It can ONLY execute Pub/Sub commands:
     `SUBSCRIBE`, `PSUBSCRIBE`, `UNSUBSCRIBE`, `PUNSUBSCRIBE`, `PING`, and `QUIT`.
   - If you tried to call `.subscribe()` on your main `redisClient`, any subsequent
     cache lookup or rate-limiting check in your application would crash with an error!
   - Therefore, subscribers MUST always have their own isolated connection.


5. KEY CHARACTERISTICS & TRADE-OFFS OF REDIS PUB/SUB
--------------------------------------------------------------------------------

Feature                       Behavior in Redis Pub/Sub
--------------------------------------------------------------------------------
Delivery Guarantee            At-most-once (Fire-and-forget).
Persistence / Storage         ZERO. Messages are never stored in memory or on disk.
Offline Clients               If a subscriber is down or restarting, it permanently
                              misses all messages sent during that window.
Fan-Out                       1-to-Many. 1 publisher can broadcast to 10,000 active
                              subscribers at the same time with sub-millisecond latency.
Receiver Confirmation         `publish()` returns the count of subscribers that heard
                              the message right now (e.g., returns `0` if nobody is listening).


6. WHEN TO USE PUB/SUB VS WHEN NOT TO USE IT
--------------------------------------------------------------------------------

✅ GREAT USE CASES:
1. Real-Time Chat & Collaboration:
   - User types a chat message -> published to room channel -> broadcast to all
     connected WebSocket servers.
2. Multi-Server Cache Invalidation:
   - When Server A updates a product in the database, it publishes "invalidate:products:10".
   - Servers B, C, and D receive the notification and evict their local memory cache.
3. Live Dashboards & Push Notifications:
   - Stock price tickers, sports scores, live follower count updates.

❌ POOR USE CASES (DO NOT USE PUB/SUB):
1. Job Processing & Background Tasks (e.g., sending emails, video transcoding):
   - If your worker crashes while processing, the job is lost forever.
   - Better Alternative: Redis Lists (`LPUSH`/`RPOP`) or Redis Streams (`XADD`/`XREADGROUP`).
2. Order Processing & Financial Payments:
   - Guaranteed delivery and persistence are mandatory.
   - Better Alternative: Redis Streams, BullMQ, Kafka, or RabbitMQ.


7. PONYTAIL AUDIT FINDINGS (ANALYSIS OF CURRENT CODE)
--------------------------------------------------------------------------------

[Finding 1] Side-Effect on Module Import in `notification.subscriber.ts`
- What happens:
  At the bottom of `src/subscribers/notification.subscriber.ts`, line 47 calls:
  `startNotificationSubscriber().catch(...)` directly in top-level module scope.
- The issue:
  `src/controllers/notification.contoller.ts` imports `publishNotification` from that file.
  This causes the Express API server process (`npm run dev`) to ALSO start a subscriber
  connection on server boot, creating an accidental duplicate subscriber alongside the
  dedicated `npm run subscriber` terminal!
- Best Practice Fix:
  Separate the publisher logic and subscriber daemon:
  - Keep `publishNotification()` in a clean service file (e.g., `src/services/notification.service.ts`).
  - Keep `startNotificationSubscriber()` strictly as a runnable daemon script in `src/subscribers/notification.worker.ts`.

[Finding 2] Dead / Unused Imports
- In `examples/redis-pub-sub.ts` (Line 14): `import { error } from 'console';` (unused).
- In `src/subscribers/notification.subscriber.ts` (Line 1): `import { error } from 'console';` (unused).
- In `src/subscribers/notification.subscriber.ts` (Line 2): `import dotenv from 'dotenv';` (dotenv is already initialized globally).

[Finding 3] Missing Dynamic Input Validation
- In `notification.contoller.ts`, `req.body.title` and `req.body.message` are not validated
  before publishing. If a client sends an empty body, `undefined` is published.
